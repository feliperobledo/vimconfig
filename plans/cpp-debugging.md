## Test project: magister

`/Users/feliperobledo/src/magister` — a small Vulkan/GLFW game engine that renders one triangle.
Surveyed 2026-11-06:

- **CMake presets drive the build.** `CMakePresets.json` defines `debug` / `release`, with
  `binaryDir = build/<preset>`. The Debug build lives in `build/debug` (Unix Makefiles,
  `CMAKE_BUILD_TYPE=Debug`, `compile_commands.json` exported) — not `build/`.
- **Targets.** Executables: `magister` (`src/main.cpp`) and `magister_engine_tests` (GoogleTest,
  `tests/engine/test_engine.cpp`). Static library: `magister_engine` (`src/engine/engine.cpp`) —
  the "library code" breakpoint target. `CMAKE_RUNTIME_OUTPUT_DIRECTORY` is the binary dir, so
  the game is `build/debug/magister`. FetchContent dependencies (GLFW, spdlog, GLM, googletest, …)
  sit under `build/debug/_deps` and must not show up as debug targets.
- **Compiler is Apple clang 21** (`/usr/bin/c++`), not the Homebrew clang 22 used in the research
  tests. Homebrew clang is first on `PATH` for `clang`/`clang++`, but with `CC`/`CXX` unset CMake
  searches for `c++` first, and only `/usr/bin/c++` provides that name (magister's
  `CMakeCXXCompiler.cmake`: `AppleClang 21.0.0`). Switching would mean setting
  `CMAKE_CXX_COMPILER` in the `base` preset; not part of this plan. So the binary uses Apple's libc++, and the "lldb-dap matches the compiler" argument no
  longer holds exactly. The formatter (step 2) must also be checked against an Apple clang build.
- **C++20**, so `std::expected` (C++23) isn't used in magister. The formatter is verified with a
  standalone program instead.
- **Runtime files.** Shaders are found relative to the executable (`whereami`), but
  `vk_layer_settings.txt` is copied next to the binary, and the Vulkan loader reads it from the
  **working directory**. So debug `cwd` = the executable's directory.
- **Vulkan env.** `~/.zshrc` only exports `VULKAN_HOME`; `setup-env.sh` isn't sourced. When
  launched from Vimspector, the game inherits Neovim's environment, so the Vulkan driver lookup
  needs checking under the debugger.
- **Signing.** `build/debug/magister` is `adhoc,linker-signed` without hardened runtime, so attach
  works without re-signing.
- **Stray in-source configure.** `CMakeCache.txt` and `CMakeFiles/` exist at the project root
  (gitignored). Target discovery must use the preset build dir and ignore these.
- `Session.vim` is used in this project, so the F2/F3 breakpoint persistence (step 4) matters here.

## Findings carried into the plan

- LLDB 22's built-in libc++ formatters render `vector`, `string`, `map`, `optional`, `variant`,
  `span`, `unique_ptr` correctly. `std::expected` renders as raw internals → step 2.
- Expression evaluation works, but only for functions present in the binary (`v.size()` works when
  the program calls it; `v[1]`, `o.value()`, `*up` fail). `settings set target.import-std-module
  true` fixes some of these but **crashed LLDB** on `m.at("b")` — keep it off.
- Vimspector applies the adapter's `configuration` first, then the project's, with a shallow
  `dict.update` (`debug_session.py:1913`). A project that sets its own `initCommands` replaces the
  adapter's list, dropping the `std::expected` formatter (built-in formatters are unaffected).
- `vimspector_process_list` (needed for `${PickProcess()}`) is looked up on `PATH`, then in the
  plugin's `support/vimspector_process_list/`; it ships as Go source only, and its built binary is
  gitignored upstream.
- Attach fails confusingly against hardened-runtime binaries without `get-task-allow`
  ("Trying to resume but the async thread is dead"). Plain `clang++` / CMake `Debug` builds are fine.

## 1. Vimspector + lldb-dap adapter — `lua/plugins/vimspector.lua`

- [ ] In `init`, define `g:vimspector_adapters["lldb-dap"]`:
  - [ ] `command` = resolved path (stdio adapter)
  - [ ] `attach = { pidProperty = "pid", pidSelect = "ask" }`
  - [ ] `configuration` defaults, including `initCommands` that import the step-2 formatter by
        absolute path (`vim.fn.stdpath("config") .. "/lldb/libcxx_expected.py"`)
- [ ] In `init`, raise `g:vimspector_sign_priority` for `vimspectorBP`, `vimspectorBPCond`,
      `vimspectorBPLog`, `vimspectorBPDisabled` and `vimspectorNonActivePC` from 9 to 12 (above
      gitgutter's 10). Keep them equal so Vimspector can combine them.
- [ ] Leave `g:vimspector_enable_mappings` unset.
- [ ] Add a `build` step that compiles the process-list helper:
      `cd support/vimspector_process_list && go build`. Confirm `go` resolves from Neovim's
      `PATH` (it lives at `/usr/local/go/bin/go`).
- [ ] In `config`, map:

  | Key | Action | `<Plug>` target |
  | --- | --- | --- |
  | `F5` | Launch / continue | `VimspectorContinue` |
  | `S-F5` | Stop | `VimspectorStop` |
  | `C-S-F5` | Restart | `VimspectorRestart` |
  | `F6` | Pause | `VimspectorPause` |
  | `F8` | Function breakpoint | `VimspectorAddFunctionBreakpoint` |
  | `F9` | Toggle breakpoint | `VimspectorToggleBreakpoint` |
  | `,F9` | Conditional breakpoint | `VimspectorToggleConditionalBreakpoint` |
  | `F10` | Step over | `VimspectorStepOver` |
  | `F11` | Step into | `VimspectorStepInto` |
  | `S-F11` | Step out | `VimspectorStepOut` |
  | `,F10` | Run to cursor | `VimspectorRunToCursor` |
  | `,Di` | Inspect value under cursor | `VimspectorBalloonEval` (n + x) |
  | `,DX` | Reset (close debug UI) | `:VimspectorReset` |

  Leader-based debug keys live under `,D`, **never `,d`**: `,d` is the `"_d` operator in normal
  and visual mode, and any `,d…` mapping would make it wait for `timeoutlen` (decided
  2026-11-08).

- [ ] Verify each key reaches Neovim in the terminal in use. If macOS takes `F11` (Show Desktop) or
      the terminal mangles `S-F*`, move step-out to `F12` and update this table.

## 2. `std::expected` formatter — `lldb/libcxx_expected.py`

- [ ] Write an LLDB synthetic-children provider + summary for `^std::__1::expected<.+>$`:
  - [ ] Summary: `has value` / `has error`
  - [ ] One child: `Value` or `Error`, rendered with its own formatter (e.g. `std::string`)
  - [ ] Locate `__has_val_`, `__val_`, `__unex_` by searching member names, not a hard-coded path
        (observed path: `__repr_.__v.__has_val_` and `__repr_.__v.__union_.__v.{__val_,__unex_}`;
        libc++ varies the layout by type)
  - [ ] `expected<void, E>`: summary only, no `Value` child
  - [ ] `__lldb_init_module` registers both providers
- [ ] Verify in plain `lldb` against a `-g -O0 -std=c++23` test program covering: value state,
      error state, `expected<void, std::string>`, a trivially-destructible `E` (e.g. `int`), and
      `expected<std::vector<int>, std::string>`.
- [ ] Repeat with the program built by **both** Homebrew clang 22 and Apple clang 21 (`/usr/bin/c++`),
      since magister uses Apple's libc++ and its `expected` layout may differ.
- [ ] Verify the same rendering through Vimspector's variables window.
